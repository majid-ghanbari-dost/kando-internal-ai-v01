## ۰. قاعده دائمی مدیریت و به‌روزرسانی هندآف

**هندآف دفتر ثبت زنده پروژه است.** دستیار در نقش Technical Manager / Chief Architect موظف است بدون نیاز به پرسش یا تأیید مجدد Product Owner، هر یافته فنی معتبر، تصمیم مصوب، تغییر وضعیت مأموریت، ریسک، نتیجه آزمون، Commit یا Artifact مرتبط با پروژه را در همین فایل ثبت و به‌روزرسانی کند.

- به‌روزرسانی باید پس از هر دستاورد مهم و پیش از تحویل گزارش مرحله‌ای انجام شود؛ نه فقط در پایان فاز.
- یافته تأییدنشده باید با برچسب فرضیه/نیازمند بررسی ثبت شود، نه به‌عنوان واقعیت.
- اگر GitHub یا ابزارها اجازه ثبت مستقیم ندهند، متن آماده و علت مانع باید در همان پاسخ اعلام شود.
- هر به‌روزرسانی GitHub باید با fetch مجدد فایل، کنترل محتوا و ثبت Commit SHA راستی‌آزمایی شود.
- این قاعده شامل تغییرات واقعی پروژه است؛ آرشیو کامل، Manifest و SHA-256 پس از تغییرات اجرایی/کدی همچنان الزامی است.

## ۱. مأموریت محصول

ساخت دستیار هوشمند داخلی Kandoo با نقش «دستیار فروشگاه»:
1. پاسخ به پرسش‌های اپراتور بر اساس اطلاعات واقعی همان فروشگاه.
2. انجام عملیات فروشگاهی فقط از طریق ابزارهای مجاز، محدود و قابل ممیزی.

این محصول چت‌بات عمومی نیست؛ دامنه آن اطلاعات و عملیات داخلی Kandoo است.

## ۲. محدوده نسخه اول

سناریوی اول: **Kandoo نرم‌افزار اصلی فروشگاه و مرجع داده عملیاتی آن است.** اتصال به نرم‌افزارهای حسابداری یا فروش خارجی فعلاً خارج از محدوده است.

نسخه اول دستیار باید ابتدا پرسش‌های خواندنی و قابل راستی‌آزمایی را پشتیبانی کند؛ عملیات تغییردهنده داده تا زمان تعریف مجوز، تأیید انسانی، idempotency و audit trail جداگانه فعال نمی‌شود.

## ۳. ایده محوری Product Owner

برای هر فروشگاه، شناخت اختصاصی و پویایی ایجاد شود تا دستیار هنگام ورود اپراتور، واقعیت همان فروشگاه را بشناسد؛ بدون آموزش مدل جداگانه برای هر فروشگاه.

این شناخت می‌تواند شامل کاتالوگ محصولات، ویژگی‌ها، دسته‌بندی‌ها، اصطلاحات محلی، aliasهای تأییدشده، روابط محصولی و قواعد تجاری تأییدشده باشد. داده‌های لحظه‌ای نباید از شناخت قدیمی خوانده شوند.

## ۴. تصمیم معماری درباره محل Store Intelligence

جهت معماری مورد توافق:
- Store Intelligence روی سیستم اصلی فروشگاه، یعنی Store Hub، مستقر شود.
- داده‌ها در پوشه‌ای تحت مدیریت Kandoo و جدا از پوشه نصب برنامه نگهداری شوند.
- برای هر فروشگاه یک شناخت معتبر وجود داشته باشد.
- Store Intelligence مشتق‌شده و قابل بازسازی است؛ مرجع حقیقت نیست.

SQLite مستقل برای Store Intelligence هنوز **پیشنهاد** است، نه تصمیم Freeze‌شده. مسیر فایل، نسخه‌بندی، Backup/Restore، هم‌زمانی و بازیابی باید در طراحی اجرایی تعیین شوند.

## ۵. معماری مفهومی

`Kandoo Database → AI Data Gateway → Store Intelligence → AI Reasoning Engine → Store-Aware Assistant`

- `Kandoo Database`: مرجع حقیقت عملیاتی.
- `AI Data Gateway`: مرز دسترسی کنترل‌شده به داده و عملیات.
- `Store Intelligence`: شناخت مشتق‌شده، نسخه‌دار و قابل بازسازی.
- `AI Reasoning Engine`: فهم درخواست و انتخاب ابزار.
- `Store-Aware Assistant`: رابط اپراتور.

قیمت جاری، موجودی لحظه‌ای، وضعیت فاکتور و فروش جاری باید از Hub خوانده شوند. مدل حق SQL آزاد یا دسترسی مستقیم به دیتابیس ندارد.

3. تکرار Operation ID با محتوای یکسان replay می‌شود؛ محتوای متفاوت با همان ID رد می‌شود.

10. Mode B صف Review جداگانه است؛ نباید به‌طور خودکار Sale یا Inventory بومی فرض شود.
11. API اختصاصی Snapshot سازگار و Change Feed صفحه‌بندی‌شده برای AI وجود ندارد.
12. مسیر SQLite در تنظیمات نسبی است و Backup پیش‌فرض غیرفعال است؛ BackupDatabase سازگار SQLite در کد وجود دارد.
13. بعضی متدهای مستقیم نوشتن وجود دارند که از `Execute` عبور نمی‌کنند؛ ممیزی تکمیلی آن‌ها در Mission 4.1 ثبت شده است.

**کشف امنیتی:** `invoice.draft_create` شماره تلفن مشتری را در Payload درخواست می‌گیرد و Payload در Outbox و Replication Log ذخیره می‌شود. Projector نباید Payload خام را به مدل یا Search Index بدهد؛ باید بر اساس Operation Type و allowlist فیلدهای لازم را استخراج و PII را حذف کند.

## ۹. Mission 4 — Store Intelligence Data Contract v0.1 (Draft)

### ۹.۱ سیاست ورود داده
- مشخصات محصولات: قابل ورود با allowlist.
- ویژگی‌های اپراتور: فقط پس از پالایش و تعریف مجوز.
- alias: فقط با منبع و تأیید مشخص.
- قیمت جاری و موجودی جاری: فقط از Hub.
- قیمت خرید: role-gated.
- PII مشتری و شماره تلفن: خارج از Store Intelligence.
- Mode B خام: خارج از شناخت؛ فقط داده‌ای که بعداً از مسیر صدور Native تأیید شده، با قرارداد مشخص قابل استفاده است.
- SalesInsights: تا اثبات Sale بومی و semantics اصلاح/ابطال فروش خارج از نسخه اول.

### ۹.۲ Snapshot Contract پیشنهادی
`snapshot_id`, `contract_version`, `store_id`, `source_schema_version`, `captured_at_utc`, `through_operation_seq`, `through_entry_hash`, `section_counts`, `snapshot_status`.

تمام بخش‌ها و high-water mark باید در یک snapshot سازگار و تراکنش خواندن واحد باشند. API فعلی این قابلیت را فراهم نمی‌کند.

### ۹.۳ Change Feed پیشنهادی
نام پیشنهادی: `ReadKnowledgeChangesAfter`.
ورودی: `store_id`, `after_operation_seq`, `after_entry_hash`, `limit`.
خروجی شامل sequence، Operation ID/Type، hash chain، زمان ثبت Hub و payload پالایش‌شده است.
- از Replication Log بخواند، نه Outbox Cloud.
- sequence و hash chain را اعتبارسنجی کند.
- عملیات ناشناخته را بی‌صدا نادیده نگیرد.
- گسست یا تغییر غیرقابل ردیابی مانع اعلام Sync کامل شود.
- پردازش تکراری idempotent باشد.

### ۹.۴ Checkpoint و Rebuild
Checkpoint پیشنهادی شامل store، sequence/hash، نسخه Projection و Contract، زمان آخرین Sync، وضعیت و کد خطا است.
Projection batch و Checkpoint باید اتمیک ثبت شوند. Rebuild باید در Generation جدید ساخته و اعتبارسنجی شود؛ نسخه قبلی تا فعال‌سازی موفق حفظ شود. بعد از Restore قدیمی، checkpoint جلوتر از دیتابیس Hub به معنی نیاز به Rebuild است.

### ۹.۵ معیارهای پذیرش SI-01 تا SI-12
Snapshot در نوشتن هم‌زمان؛ sequence بدون شکاف؛ replay بدون اثر تکراری؛ Crash بدون Checkpoint کاذب؛ توقف روی hash نامعتبر؛ مدیریت عملیات ناشناخته؛ تشخیص Restore قدیمی؛ حذف PII؛ عدم پاسخ لحظه‌ای از Projection قدیمی؛ عدم تبدیل Mode B به Sale؛ Rebuild قابل مقایسه؛ عدم اختلال Hub هنگام خرابی شناخت.

## ۱۰. Mission 4.1 — ممیزی مسیرهای نوشتن (نتیجه اولیه و موارد باز)

### شواهد تأییدشده از کد
1. `SqliteHubStore.SaveProduct`, `AppendInventory` و `SaveInvoice` در `SqliteHubStore.cs` از helper خصوصی `Write(...)` استفاده می‌کنند.
2. helper `Write` فقط تراکنش SQLite را باز می‌کند، callback را اجرا و Commit/Rollback می‌کند؛ Operation، Outbox و Replication Log تولید نمی‌کند. بنابراین استفاده عملیاتی از این wrapperها تغییر غیرقابل ردیابی برای Change Feed مبتنی بر Operation Log ایجاد می‌کند.
3. `RegisterProduct` و `RetireProduct` در `SqliteHubStore.ProductCatalog.cs` از `Execute` استفاده می‌کنند؛ ثبت محصول و موجودی اولیه در همان Operation انجام می‌شود.
4. `HubOperationService` برای تغییرات فاکتور و محصول، مسیر `_store.Execute` را طی می‌کند و تغییرات دامنه را در همان تراکنش ثبت می‌کند.
5. `CompleteTimeout` در `SqliteHubStore.cs` از `Write` استفاده می‌کند و می‌تواند DraftLock و فاکتور را تغییر دهد، بدون آنکه Operation/Outbox/Replication Log جدید ثبت کند. این یک مسیر عملیاتی مهم و Blocker برای Change Feed است.
6. `RestoreReplayedState` در `SqliteHubStore.Restore.cs` مستقیماً Transaction-level write انجام می‌دهد؛ این مسیر بازیابی است و در همان تراکنش، Operations و Replication Entries بازیابی‌شده را نیز درج می‌کند. این مسیر نباید به‌عنوان تغییر عملیاتی عادی طبقه‌بندی شود.
7. `SaveModeBReview` در `SqliteHubStore.ModeBReview.cs` وضعیت صف Review و اصلاحات آن را در جداول مستقل ثبت می‌کند و Operation Log بومی تولید نمی‌کند. این داده‌ها باید در صورت نیاز به AI، به‌عنوان جریان جانبی با قرارداد و ممیزی جداگانه بررسی شوند؛ منبع Sale/Inventory نیستند.
8. صدور نهایی Mode B از طریق `HubOperationService` و عملیات Native فاکتور انجام می‌شود؛ سپس وضعیت Review جداگانه به ISSUED تغییر می‌کند.

### طبقه‌بندی موقت
- **Operational و دارای Operation Log:** مسیرهای `Execute`، از جمله Product Catalog و عملیات `HubOperationService`.
- **Operational و فاقد Operation Log:** `CompleteTimeout`؛ باید اصلاح یا در قرارداد Change Feed به‌صورت مستقل پوشش داده شود.
- **Wrapperهای عمومی با خطر bypass:** `SaveProduct`, `AppendInventory`, `SaveInvoice`؛ call siteهای کل ریپو هنوز باید کامل فهرست شوند و هر مصرف عملیاتی باید حذف/محدود یا به Operation تبدیل شود.
- **Restore/Recovery:** `RestoreReplayedState`؛ مجاز به درج مستقیم فقط در مسیر بازیابی کنترل‌شده و دیتابیس هدف تازه است.
- **Auxiliary Review:** `SaveModeBReview`؛ خارج از Operation Log دامنه، نیازمند قرارداد جدا در صورت ingestion.
- **Tests/Seed/Import:** call-siteهای کل ریپو هنوز به‌طور کامل شمرده نشده‌اند؛ تا تکمیل این جست‌وجو ادعای «تمام مسیرهای نوشتن ممیزی شد» مجاز نیست.

### وضعیت Mission 4.1
**در حال انجام — نتیجه اولیه معتبر، اما هنوز قابل بستن نیست.** بررسی Interface نیز تأیید کرد که `IHubStore` به‌صورت عمومی `SaveProduct`, `AppendInventory`, `SaveInvoice` و `CompleteTimeout` را عرضه می‌کند؛ بنابراین خطر bypass صرفاً داخلی یا نظری نیست و مرز API عمومی Store نیز باید اصلاح/محدود شود. `IHubTransaction` primitiveهای نوشتن را برای استفاده داخل تراکنش تعریف می‌کند؛ این سطح باید از دسترسی عمومی عملیاتی تفکیک شود. پروژه Hub روی `.NET 8`, زبان C# 12 و Nullable/TreatWarningsAsErrors ساخته می‌شود. ریپوی AI در بررسی فعلی فقط فایل هندآف را دارد و هنوز Solution یا کد اجرایی ندارد.

موارد باز:
- استخراج فهرست کامل call siteهای wrapperهای مستقیم در تمام پروژه‌ها و تست‌ها.
- تعیین تکلیف دقیق `CompleteTimeout` و تمام تغییرات DraftLock.
- بررسی تمام مسیرهای SQL مستقیم و متدهای عمومی Store که می‌توانند Product/Inventory/Invoice را تغییر دهند.
- تعیین اینکه Mode B Review آیا در شناخت AI لازم است یا خیر؛ پیش‌فرض نسخه اول: خیر.
- افزودن تست اثباتی برای پوشش کامل Write Path، پیش از ساخت Snapshot/Change Feed.

## ۱۱. Technical Challenge و Blockers پیش از اتصال AI به داده عملیاتی

**حاکمیت اتصال:** مطابق دستور صریح Product Owner در ۱۲ نوامبر ۲۰۲۶، اتصال به Kandoo Hub تحت نظارت و اختیار مدیر پروژه Kandoo است. تیم AI فقط هسته مستقل، Fake Gateway، قراردادهای قابل تست، مستندات و آداپترهای تستی را می‌سازد. هیچ اتصال زنده، دسترسی به دیتابیس Hub، استفاده از credential واقعی، migration، تغییر کد/Schema ریپوی مادر یا عملیات خواندن/نوشتن روی فروشگاه انجام نمی‌شود، مگر پس از تحویل ریپو، بررسی مدیر پروژه و تأیید صریح او. عبور از blockerهای فنی به‌تنهایی مجوز اتصال نیست.

- **B1 — Write-path closure:** هیچ تغییر عملیاتی Product/Inventory/Invoice نباید بیرون از قرارداد ثبت/replay بماند. `CompleteTimeout` و wrapperهای مستقیم هنوز مانع‌اند.
- **B2 — Snapshot consistency:** تراکنش خواندن سازگار و high-water mark باید با تست هم‌زمانی واقعی اثبات شود.
- **B3 — Change Feed API:** API مستقل، صفحه‌بندی‌شده، hash-validated و مستقل از Outbox Cloud لازم است.
- **B4 — PII/allowlist:** Projector باید فیلدهای مجاز را از Operationهای شناخته‌شده استخراج کند؛ Payload خام ممنوع.
- **B5 — Invoice/Sale semantics:** فاکتور صادرشده را Sale بومی فرض نکنیم. تا روشن شدن مدل فروش/ابطال/اصلاح، تحلیل فروش و موجودی فروش‌محور ساخته نشود.
- **B6 — Mode B side stream:** وضعیت Review جریان کمکی است و فقط با نیاز محصول و قرارداد مجزا بررسی می‌شود.
- **B7 — Deployment/Recovery:** مسیر داده مستقل، Backup/Restore، نسخه schema و خرابی Store Intelligence باید طراحی و تست شود.

## ۲۰. Build 0.2.2 — Ambiguity & Clarification (پیاده‌سازی؛ CI در انتظار)

### هدف و Technical Challenge
مشکل Build 0.2.1 این بود که Gateway می‌توانست چند محصول مشابه برگرداند، اما AssistantService هنوز قرارداد روشن و machine-readable برای «عدم انتخاب» و درخواست توضیح نداشت. در درخواست قیمت/موجودی، انتخاب خودکار یکی از چند محصول می‌تواند پاسخ مالی/موجودی نادرست تولید کند؛ بنابراین انتخاب دلخواه ممنوع است.

### تصمیم‌های فنی این برش
1. وضعیت حل درخواست به پاسخ افزوده شد: `ResolutionStatus`.

5. وضعیت‌های `resolved`, `not_found`, `query_required`, `unsupported` از هم تفکیک شدند.
6. در نمونه stateless فعلی، اپراتور باید درخواست را با نام کامل یا کد محصول تکرار کند؛ state مکالمه یا انتخاب پنهان روی سرور ذخیره نمی‌شود.
